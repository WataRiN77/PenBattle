# STORY · 《PenBattle》毕业设计开题答辩

## 受众与场景
- 听众：毕业设计开题答辩评审组（专业教师）
- 时长：10–15 分钟；页数 18 页
- 目标：让评审相信「这个题目**值得做、做得完、做得出来、且我知道怎么判断它成功**」

## 叙事主线（一句话）
> 我想做的不是一个"弹笔小游戏"，而是**验证：在回合制对战里用实时物理来结算战斗，能不能既保证结果可复现、又给玩家足够的策略空间**。

## 起承转合
1. **起（P1–P4）先把题目讲小**
   - 课题 ≠ 项目：项目是《PenBattle》，课题是"物理结算机制的可行性与设计方法"
   - 抛出 1 个主问题 + 3 个子问题，每个子问题配一个可执行的验证方式
   - 目的：让评审觉得"题目小、边界清、能落地"

2. **承（P5–P8）证明这个题目站在已有工作之上**
   - 物理驱动玩法（Rocket League / Human Fall Flat）
   - 派对合作类（Overcooked 分手厨房 / It Takes Two 双人成行）
   - 构筑类（Slay the Spire）
   - 技术既有方案（Networked Physics、确定性回放、回滚 netcode）
   - 落点：三条线交汇处（回合制 × 实时物理 × 构筑）**目前缺少面向小团队/原型的轻量验证**

3. **转（P9–P14）讲我怎么做**
   - 技术为主（P9–P12）：物理参数分离 → 三层时序与状态机 → 联机一致性与事件驱动
   - 设计模式为辅（P13）：事件驱动 + 数据驱动配置化 + 状态效果双轨
   - 产品支撑（P14）：用户画像、场景、竞品对标
   - 每一页都对应**已经做出来的东西**，能讲出实现细节

4. **合（P15–P18）讲清楚成果与判断标准**
   - 创新点 3 条（小而具体）+ AI 辅助开发的实证
   - 预期成果（原型级，不夸大）+ 评估方法（工程自测 + 小样本问卷 + 对局数据）
   - 进度计划与风险应对
   - 致谢

## 每页的论证角色
| 页 | 角色 | 这一页要说服评审的点 |
|---|---|---|
| P1–P2 | 仪式 | 正式、完整 |
| P3–P4 | hero | 题目小、问题清、可验证 |
| P5–P8 | supporting | 有依据、不是拍脑袋 |
| P9–P12 | hero | 技术有深度、且已实现 |
| P13–P14 | supporting | 设计有章法、用户有定位 |
| P15–P16 | hero | 创新点具体、成果可衡量 |
| P17–P18 | 收束 | 计划可行、风险可控 |

## 语言与口径纪律
- 不编造销量/在线数：数据位留占位符，标注需查来源
- 不夸大：只说"在局域网 2–4 人原型范围内验证可行性"
- 术语统一：小局 / 回合 / 行动 三层定义全文一致
- 未做之事（联机同步、UI、AI 对手）明确标为"计划中/展望"
