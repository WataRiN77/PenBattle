## 0. 目标与范围

**目标**：2~4 人局域网（后续可扩展互联网）联机对战，房主（Host）权威结算。

**本阶段做**：
- Host / Client 直连（IP + 端口）
- 笔的物理与位置同步（主机算，客户端跟随）
- 输入上报 + 回合归属校验（防作弊）
- 回合状态机、积分、淘汰的权威同步
- 地图选图的权威同步（保证各端同一张图）

**本阶段不做**（明确边界，避免摊大）：
- **互联网房间（房间号 + 密码）**：原计划走 Unity Relay，因 Unity 2026-06-30 关停国区服务（HTTP 451）而回滚，见 §2.4
- 房间列表 / 匹配大厅 / 好友系统 / 账号
- 断线重连的完整状态恢复（只做基础容错）
- 物理确定性重演（lockstep / rollback）→ 属于**研究性探索**，见 §7

## 1. 现状盘点（会被横切的模块）

| 模块 | 现状 | 联机后要变成 |
|---|---|---|
| `GameManager` | 单机回合状态机；`IsMyTurn(penId)` 本地判定；直接广播权威事件 | **只在主机跑**；状态用 `NetworkVariable` 下发；客户端只读 |
| `InputManager` | 鼠标选笔/蓄力/发射；`LaunchPen()` 直接 `pen.Launch()` | 客户端**只上报**；主机校验后执行；本地只做表现 |
| `PenController` | Rigidbody 物理、耐久、碰撞事件；**Rigidbody 挂在子物体上** | 物理只在主机跑；客户端插值；**预制体需拍平**（见 §4.1） |
| `MapManager` | 每小局随机抽图（已有 `seed`） | **主机抽**，`mapId` 下发，客户端装同一张 |
| `MatchSetupManager` | `OnGUI` 本地依次选笔 | 各端**各自**选自己的笔，选择上报主机 |
| `UpgradePhaseManager` | `OnGUI` 本地依次抽强化 | 各端**各自**抽自己的，选择上报主机 |
| `EventBus` | 全局发布/订阅，玩法逻辑靠它解耦 | **保持本地**，仅用于表现层；权威事件改由主机产生后再同步 |
| 技能 / 被动 / 状态效果 | 各自订阅事件、直接改数值 | 效果逻辑**只在主机生效**；只同步结果（耐久/层数/摩擦） |

## 2. 网络架构总览

### 2.1 权威模型：Host-Authority（房主权威）
- **Host** = 服务器 + 玩家：算物理、判规则、出结果
- **Client** = 上报操作、接收状态、本地插值表现
- **为什么选它**：局域网延迟低、实现成本可控、无需独立服务器；也是本项目开题里 RQ-a 的验证对象
- **反例（不做）**：各端各自算物理 → 必然分叉

### 2.2 一次"发射"的完整时序

```
Client（行动方）                         Host
────────────────────────────────────────────────────────────
鼠标操作（选笔/拖拽/蓄力）  ← 纯本地表现
  ↓ 松开
ServerRpc SubmitLaunch(penId, direction, force, point)
                                        ├ 校验：IsMyTurn? phase==Action?
                                        ├ 校验：force <= maxLaunchForce（防作弊）
                                        ├ pen.Launch(...)  ← 权威物理在这里发生
                                        └ 广播结果
Client 收到笔的位置/速度同步  ←───────────┘
（本地插值显示，不再自己算）
```

### 2.3 三条铁律
1. **客户端不产生任何权威状态**：位置、耐久、积分、回合归属都只信主机
2. **客户端不执行玩法逻辑**：技能/被动/状态效果的效果计算只在主机跑
3. **UI/表现层可以本地跑**：牵引线、落点指示、高亮、相机——这些不影响胜负

---

### 2.4 互联网房间：为什么暂时不做（Unity Relay 已被地区限制）

**原始设想**：主机建房拿「房间号 + 密码」，客户端凭号进房，走 Unity Relay 中继。
代码写过一版（`RelayRoom.cs` + `NetworkLauncher` 的房间模式），**实测直接失败**：

```
Unity.Services.Relay.RelayServiceException: HTTP/1.1 451 Unavailable For Legal Reasons
```

**根因（不是代码问题）**：Unity 官方公告 —— **自 2026-06-30 起，注册地在中国大陆 / 中国香港 / 中国澳门的组织
不能再用绝大部分 Unity 全球 Gaming Services**，请求统一返回 **HTTP 451 / "Unavailable in your region"（错误码 53）**。

- 停用：**Relay、Lobby、Matchmaker、Vivox、Cloud Code、Cloud Save、Analytics、CCD** 等
- 保留：**Ads、In-App Purchasing、Authentication**
- 判定依据是**组织注册地**，与玩家位置、目标市场无关

> 这也是为什么报错前一步的匿名登录（Authentication）是成功的 —— 容易误判成"只差最后一步"。
> 结论：**在这个账号体系下，Unity Relay 这条路走不通，换写法 / 换区域都没用。**

**已回滚**：`RelayRoom.cs` 删除，`com.unity.services.relay` 从 manifest 移除，
`NetworkLauncher` / `ConnectPanelUI` 恢复成纯局域网版本。当前联机 = **局域网 / 直连 IP**。

#### 将来要接互联网联机，可选路线（都不免费或都要额外配置）

| 路线 | 房间号+密码 | 成本 | 代价 |
|---|---|---|---|
| **UOS Sync Relay**（Unity 中国） | ✅ 私密房需密码 | 微 0.2 元/房/天 + 下行 1.2 元/GB；**试用 50 个房间** | 换 `RelayTransportNetcode`（NGO 逻辑可留），需 UOS App + Room Profile UUID |
| **ZeroTier / Tailscale 虚拟局域网** | 用虚拟 IP 代替 | 永久免费（ZT 10 设备 / TS 6 用户） | 每个玩家要装客户端 |
| **公网 IPv6 直连** | 用地址代替 | 免费 | 需双方宽带都有公网 v6 且放行入站；走 `SetConnectionData(NetworkEndpoint)` |
| **自建房间服务 + Dedicated Server / frp** | ✅ 自己实现 | 云主机 10~40 元/月 | 工作量最大，要运维 |

**关键取舍**：「零配置 + 永久免费 + 6 位房间号」三者不可兼得 —— 这三个原本是 Unity Relay 一家提供的。
论文里这一段可以直接作为"第三方联机服务可用性风险"的案例写。

### C. 输入改造（核心）
- [ ] `InputManager` 只保留"采集输入"，不再直接调用 `pen.Launch()`
- [ ] 新增 `ServerRpc SubmitLaunch(uint penId, Vector3 dir, float force, Vector3 point)`
- [ ] `ServerRpc SubmitPlace(uint penId, Vector3 targetPos)`（对应 `GameManager.PlayerPlacePen`）

- [ ] 本地"我的回合"判断：用 `NetworkManager.LocalClientId → playerId` 比对，而不是现在的"谁都能选中"
- [ ] **验收**：非行动方的客户端点笔点不动；改包伪造也能被主机拒绝（Console 有拒绝日志）

### D. 笔的同步
- [ ] 笔预制体加 `NetworkObject`
- [ ] 主机算物理 → 客户端用 `NetworkTransform`（或 `NetworkRigidbody`）跟随
- [ ] 客户端本地 Rigidbody 设 `isKinematic = true`（只做插值，不自己模拟）
- [ ] 同步内容：位置、旋转、速度（速度用于插值平滑）
- [ ] **验收**：主机弹笔，客户端看到的轨迹平滑、落点一致

### E. 回合状态机同步
- [ ] `GameManager` 只在主机执行 `StartNewRound` / `StartTurn` / `NextTurn` / `EndRound`
- [ ] 需要下发的状态：`roundNumber`、`turnNumber`、`currentPlayerIndex`、`phase`、各玩家 `score`、`isEliminated`
- [ ] 用 `NetworkVariable`（或主机 `ClientRpc` 广播）同步；客户端**只更新 UI**
- [ ] 同步现有事件：`RoundStartEvent` / `TurnStartedEvent` / `ActionStartedEvent` 等 → 改由主机同步后，客户端**重播**给本地 UI
- [ ] **验收**：两端显示"轮到谁"完全一致

### F. 地图选图同步
- [ ] 选图**只在主机**执行：`MapManager.SelectAndApply()` 仅主机调用
- [ ] 主机把 `mapId` 下发（`NetworkVariable<FixedString64>`）；客户端收到后 `Instantiate` 同一张地图 prefab
- [ ] 已有 `seed` 字段保留：主机定 seed → 各端用同 seed 抽图（对"可复现性"研究是加分项）
- [ ] **验收**：每小局两端地图**完全一致**（含障碍物布局、出生点）
- [ ] ⚠️ 客户端**不要**调用 `SelectAndApply()` 里的随机逻辑

### G. 选笔 / 强化阶段
- [ ] `MatchSetupManager` 从"本地依次选"改为"**各端选各自的**"，`PlayerSetupConfirmedEvent` 改为上报主机
- [ ] `UpgradePhaseManager` 同理：各端各自抽卡/选择 → 上报主机 → 主机确认
- [ ] 主机收齐所有选择后才推进流程
- [ ] **降级方案**（如果时间紧）：这两个阶段先做成"主机单方代选"，联机只做对战部分——**须在报告里写明这是简化**

### H. 技能 / 被动 / 状态效果
- [ ] 效果逻辑（造成伤害、叠燃烧、冰冻改摩擦）**只允许主机执行**
- [ ] 客户端侧这些组件**禁用**（或加 `if (!IsServer) return;` 守卫）
- [ ] 只同步**结果**：`PenController` 的耐久、状态效果列表与层数、摩擦/质量等被改过的物理参数
- [ ] **验收**：荆棘反弹、燃烧、冰冻在两端表现一致，且不重复触发

### I. 淘汰与结算
- [ ] `PenEliminatedEvent` 只由主机产生 → 同步 `isEliminated`
- [ ] 积分、小局胜负、比赛胜负只在主机判定
- [ ] **验收**：两端结算画面一致

### J. 容错（基础版）
- [ ] 客户端掉线：主机标记该玩家淘汰（或托管），比赛继续
- [ ] 超时：主机的 `maxActionTime` 计时为准，客户端只显示
- [ ] 完整重连（状态恢复）**列为后续**
- [ ] **验收**：拔网线不至于卡死

## 4. 关键取舍

### 4.1 ⚠️ 先拍平笔预制体（强烈建议，放在最前面做）
现在 `笔1.prefab` 的 **`Rigidbody` + `PenController` 挂在子物体**上、根节点还带一个烘焙偏移 `(-7.48, 0.5, -5.87)`。这已经踩过两次坑：
1. 改根节点 `position` 不生效（移动 Rigidbody 的父物体不算传送 → 09-23 那个"两支笔出生在同一点"）
2. 联机后 NGO 要求 `NetworkObject` 在预制体根、`NetworkTransform` 与 Rigidbody 同物体 → 现状会很别扭

**做法**：把 `PenController + Rigidbody + Collider` 移到预制体根节点，删掉根上的烘焙偏移，让"一支笔 = 一个对象"。
**收益**：传送直觉正确、NGO 配置简单、`SetSpawnRoot` 那套补丁可以简化掉。

### 4.2 物理同步 vs 确定性重演
| 方案 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| **变换同步**（`NetworkTransform`） | 实现快、稳 | 带宽略高、客户端看到的是"插值" | **先做这个跑通** |
| 确定性重演（lockstep/rollback） | 带宽极低、可复现 | 要求物理完全确定性，工程量大 | 作为 §7 的**研究探索**，不作为必达 |

### 4.3 EventBus 怎么处理
- **保留**：表现层（特效、音效、UI、相机）继续用 EventBus，各自本地播
- **改造**：权威事件由主机产生后，通过 NGO 同步；客户端收到后**再**本地 `Publish` 一次给 UI 用
- **铁律**：客户端**禁止**通过 EventBus 触发任何会改变权威状态的逻辑

### 4.4 数据同步方式一览
| 数据 | 方式 | 频率 | 权威 |
|---|---|---|---|
| 笔 Transform / 速度 | `NetworkTransform` | 每帧/按需 | 主机 |
| 耐久 `_currentStatusDurability` | `NetworkVariable<float>` | 变化时 | 主机 |
| 状态效果（类型/层数/剩余回合） | `NetworkList` 或 RPC | 变化时 | 主机 |
| 回合状态（phase/round/turn/currentIndex） | `NetworkVariable` | 变化时 | 主机 |
| 积分 / 是否淘汰 | `NetworkVariable` | 变化时 | 主机 |
| 当前地图 mapId | `NetworkVariable<FixedString64>` | 每小局 | 主机 |
| 玩家操作（发射/放置/技能） | `ServerRpc` | 操作时 | 客户端上报 |
| 蓄力条 / 牵引线 / 高亮 | **不同步** | — | 纯本地表现 |

## 6. 风险与应对

| 风险 | 应对 |
|---|---|
| 物理同步抖动/漂移 | 客户端 kinematic + 插值；关键事件（发射、碰撞）用主机权威结果覆盖 |
| 两个客户端看到不同回合 | 回合状态全部由主机 `NetworkVariable` 驱动，客户端不自行自增 |
| 拍平预制体影响现有物理手感 | M2 单独做并回归测试；`PenController` 的物理参数来自 `PenConfig`，与层级无关 |
| 选笔/强化阶段网络化工作量大 | 见 §3.G 降级方案（主机代选），但要在报告里写明 |
| 时间不够 | 先保 M1~M4（可演示），M5~M8 视进度 |

## 7. 与开题 RQ 的对应（答辩要用）

- **RQ-a（技术）**：小规模联机下物理同步与回合状态机的衔接
  - 指标：**同步延迟**（主机操作 → 客户端可见的毫秒数）、**状态一致率**（两端关键状态比对一致的次数 / 总次数）、帧率
  - 做法：每小局记录两端的状态快照（回合归属、耐久、积分）做一致性比对；用网络条件（局域网 + 人为加延迟）做对比
- **RQ-b（设计）**：构筑在有限内容量下的策略多样性 → 联机后统计**多人的构筑选择分布**，比单机更有说服力
- **RQ-c（方法）**：AI 辅助开发提效 → **本阶段的开发过程要留痕**（哪些模块 AI 一次过、哪些反复返工）
- **可复现性**：`MapManager.seed` + 固定物理步长 → 可用于"相同初始条件 + 相同操作序列 → 一致结果"的实验
