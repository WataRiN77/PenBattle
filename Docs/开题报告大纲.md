## 0. 基本定位

| 项 | 内容 |
|---|---|
| 作品名 | 《PenBattle》弹笔对战 |
| 作品副标题 | 基于实时物理模拟的多人联机多维度构筑对战游戏 |
| 研究类型 | **设计实践型研究**（原型实现 + 用户评估），技术章节占主导 |
| 建议主标题 | 回合制框架下实时物理结算的确定性与策略性研究 —— 以《PenBattle》为例 |

### 研究问题（RQ）
**主问题**：在回合制框架下以实时物理模拟作为战斗结算机制时，如何在保证**结果可复现性**与**联机一致性**的前提下，提供足够的**策略深度**？

**子问题**：
- RQ-a（技术）：小规模联机（局域网 / 房主权威）下，物理状态同步与回合状态机如何衔接？
- RQ-b（设计）：基于"通用池 + 笔专属池"的随机三选一构筑，在有限内容量下能否提供足够策略多样性？
- RQ-c（方法）：AI 辅助开发工具在本项目的实践中，对开发效率与质量的影响如何量化？

## 2. 逐页大纲（约 16 页）

### 第一部分：研究课题（2 页）
**P1 封面** — 学校 / 学院 / 专业 / 姓名 / 指导教师 / 日期
**P2 目录**
**P3 论题选择**

- 项目 = 《PenBattle》作品；课题 = 物理结算机制的可行性与设计方法

### 第二部分：研究背景与意义（4 页）
**P5 物理驱动玩法的兴起**
- 案例：Rocket League（物理载具对战）、Human Fall Flat / Gang Beasts（软体物理的不可预测乐趣）
- 论点：物理模拟带来 **emergent gameplay（涌现式玩法）**
- 数据：销量 / 同时在线（**标可查来源：Steam 官方、VGChartz**）
**P6 派对/合作类游戏的现象级案例（重点）**
- **《Overcooked 分手厨房》**：强协作、短时长、高重玩、社交传播
- **《It Takes Two 双人成行》**：TGA 年度游戏，双人合作天花板
- 对我们的启发：短对局 + 明确反馈 + 可重复
**P7 构筑（Deck-building）玩法的策略深度**
- 案例：Slay the Spire（杀戮尖塔）、Monster Train
- 论点：**随机三选一 + 累加构筑** 用小内容量换大策略空间
- 对应本作：通用池 + 笔专属池 → 每次随机 3 选 1
**P8 技术背景与既有方案**
- 确定性物理与网络同步：Glenn Fiedler《Networked Physics》系列
- GDC：Overwatch Replay System（确定性回放 / ECS）
- 回滚网络代码（GGPO / Rollback netcode）思路
- 论点：已有方案面向大团队大场景；本项目关注**小规模场景下的轻量可行解**

### 第三部分：我要做什么（4 页）
**P9 【主】技术探索**
- 实时物理：质量 / 弹性 / 摩擦 / 线性阻尼 **四参数分离**（工程踩坑：曾把 friction 当 drag 用）
- 三层时序：**行动 → 回合 → 小局**（术语已明确定义）
- 确定性：同一初始状态 + 同一操作序列 → 一致结果
- 联机：房主权威（Host Authority）+ Unity Transport，局域网优先
- 事件驱动 EventBus 解耦
**P10 【次】设计模式探索**
- 事件驱动架构（自研 EventBus）
- 状态机：Idle → Action → Resolving → RoundEnd → MatchEnd
- 数据驱动：ScriptableObject 配置化（笔、技能、被动、强化均为数据资产，不改代码即可扩展）
- 状态效果系统：层数制（燃烧）/ 持续回合制（冰冻）双轨
**P11 【支撑】产品设计**
- 用户画像、场景、竞品对标（见 P12–P13）
**P12 用户与场景**
- 用户：18–30 岁，学生 / 初入职场；有"课桌弹笔"共同记忆；偏好短时长、高重玩、低门槛
- 主场景：**朋友间轻量对战**（局域网 / 线上）
- 次场景：**本地热座 / 练习模式**（私人碎片时间）
- ⚠️ 说明：本作**不含游戏内 AI 对手**，私人场景由热座与练习覆盖
**P13 竞品对标与差异化**
- 对比表：Rocket League / Overcooked / Slay the Spire
- 我们的位置：回合制 × 实时物理 × 构筑（三者交叉点）

### 第四部分：课题细节（3 页）
**P14 游玩后目标**
- 记住：怀旧共鸣（弹笔这一共同记忆）
- 再来一局：单局 3–5 分钟、强随机性
- 传播：派对游戏天然具备口碑传播属性
**P15 创新点（小而具体，3 条）**
1. 物理参数与状态效果的**解耦设计**（四参数分离 + 状态效果叠加规则）
2. 回合制状态机与实时物理结算的**衔接机制**（三层时序 + 物理静止判定）
3. 通用池 + 笔专属池的**随机三选一构筑**：小内容量换策略多样性
**P16 【+1】AI 辅助开发的实证**
- 定位：AI 是**开发工具**，不是游戏内容
- 记录维度：shader 编写、架构重构、问题定位的**耗时与迭代次数**
- 对照：传统查找资料 vs AI 协作（同一类任务的耗时对比）
- 结论取向：给出**经验总结**（哪些环节提效明显、哪些环节 AI 不可靠）

### 第五部分：预期成果与验证（2 页）
**P17 预期成果**
- 可玩原型（垂直切片）：完整单局循环 + 4 人联机
- 5 支笔 + 被动 / 状态效果 / 强化构筑系统
- 设计文档 + 技术文档 + 测试报告
- **体量声明**：小型可玩原型，**非完整商业产品**
**P18 评估方法（设计/作品型口径）**
- 工程自测：物理一致率（相同初始条件下结果一致比例）、同步延迟、帧率
- 玩家反馈（小样本问卷，Likert 5 点）：乐趣、策略深度、公平感、操作手感
- 对局数据：单局时长、构筑选择分布（验证是否出现"唯一最优解"）
- 开发过程数据：AI 辅助提效记录
- **不夸大**：小样本、局域网、原型级；结论限定在"该原型范围内可行"

### 第六部分：计划与风险（2 页）
**P19 进度计划**
1. 核心玩法与物理手感 → 2. 放置操作 → 3. 选笔/技能 UI → 4. 开局强化 → 5. 败者强化 → 6. 网络层（房主权威）→ 7. UI 打磨
**P20 风险与应对**
- 联机同步复杂度 → 局域网优先、房主权威、缩小人数规模（2–4 人）
- 物理不确定性 → 固定时间步长、关键参数不依赖浮点累积
- 时间风险 → 先做垂直切片，内容量后置

## 4. 写作原则（答辩自保）

1. **不编数据**：所有销量 / 在线数标注可查来源；不确定的写"约"或换成定性描述
2. **不夸大**：不说"解决联机同步难题"，说"在小规模局域网场景验证了房主权威方案的可行性"
3. **题目要小**：创新点 3 条、每条都能讲出实现细节
4. **方法清晰**：设计实践型 = 原型实现 + 用户评估 + 工程自测；不装成严格的科学实验
5. **术语一致**：小局 / 回合 / 行动 三层定义全文统一（这是本作的术语约定）
